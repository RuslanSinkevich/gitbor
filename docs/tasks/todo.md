## Задача 1 — Учётные данные Git (HTTPS / корпоративный пароль)

**Проблема:** после смены корпоративного пароля push/fetch падают с `Authentication failed` (TFS/Azure DevOps по HTTPS). В «Настройках репозитория» сейчас только имя и email — обновить пароль нельзя.

**Что сделать:**
- Добавить в «Настройки репозитория» (или отдельный блок «Доступ к remote») действие вроде «Обновить пароль» / «Сбросить сохранённые учётные данные».
- По нажатию: очистить старые credentials для URL текущего `origin` (через `git credential`), показать форму логин + пароль (PAT/корпоративный пароль), сохранить новые.
- Показывать блок только для HTTPS-remote; для SSH — ссылка на настройки SSH-ключей (уже есть в меню).
- Опционально: при ошибке `auth` в журнале Git — кнопка «Обновить учётные данные», открывающая тот же диалог.

**Заметки:** бэкенд `CredentialHelper` уже есть, нужен IPC + UI. Не путать с git `user.name` / `user.email`.

**Сделано (2026-06-06):** реализуемо, но НАДЁЖНОСТЬ зависит от настроенного `credential.helper` — это и есть «управление ОС-хранилищем». ## Задача 3 — Диалог Push, когда цель неоднозначна

**Проблема:** если у ветки есть upstream, GitBor сразу делает `git push`. При несовпадении имён локальной ветки и upstream Git отказывает (`push.default = simple`), а пользователь видит «неизвестную ошибку». Fork в такой ситуации открывает окно Push (локальная ветка, remote, «куда» с дефолтом из upstream).

**Когда показывать диалог вместо слепого push:**
- нет upstream (уже так);
- **имя локальной ветки ≠ имя ветки в upstream** (после отсечения `remote/`);
- опционально: несколько remote, куда логично пушить, и нельзя выбрать один однозначно.

**Что сделать:**
- В `runPush`: при любом из условий выше — модалка (remote + целевая ветка), дефолт «куда» = upstream, если он есть, иначе имя локальной ветки.
- Push через `pushTo` с явным `HEAD:<branch>`, при необходимости `-u`.
- Распознать stderr про mismatch upstream / предложить тот же диалог повторно, а не только generic `unknown`.

**Ориентир UX:** как Fork — пользователь всегда видит, *куда* уйдут коммиты, если приложение не уверено на 100%.

**Сделано (2026-06-04):**
- `pushDestination.ts`: `canPushDirectly` / `upstreamBranchShort` — plain push только при совпадении локального имени и upstream.
- `useSyncActions.runPush`: иначе модалка; дефолт «куда» = upstream при расхождении имён; в списке веток — upstream и локальная, если их нет после fetch.
- Тесты: `tests/hooks/pushDestination.test.ts` (8 кейсов). Прод-сборка `dist:win` ок.
- **Не сделано:** классификатор stderr + повторный диалог после fatal mismatch.

**Сделано (2026-06-06):** `pushDestination.isPushDefaultMismatch(stderr)` — матчит каноничный текст git «upstream branch of your current branch does not match the name of your current branch» (whitespace/case-tolerant), НЕ матчит non-fast-forward и no-upstream. `useSyncActions` вынес `openPushDialog` (форсит диалог минуя plain-push) и экспортит его. В `App.tsx` эффект на `lastOpResult`: push + mismatch → повторно открываем диалог; generic-toast подавлен через `willShowModal` (расширен `operation`+`error`). +5 тестов в `pushDestination.test.ts` (всего 15).

**Регрессия (исправлено):** модалка всплывала всегда — `canPushDirectly` резал upstream по первому `/`, ломая вложенные пути (`remote/feature/...`). Сравнение через `endsWith('/' + local)` + `upstreamBranchShort` с префиксом remote.

**Ревью:** нужна перепроверка сильной моделью — логика `canPushDirectly`, дефолты в диалоге, краевые случаи (несколько remote, смена remote в модалке, force push), не сломали ли сценарий «первый push без upstream».

## Задача 4 — Track Remote Branch (локальная ветка с tracking)

**Проблема:** в Fork из «Удалённые» можно «Track Remote Branch» — создать локальную ветку с upstream на выбранную remote-ветку (редактируемое имя, кнопка Track). В GitBor для remote-ветки в меню только Checkout (часто detached / не то) и «новая ветка от ref» — нет явного «перенести к себе с tracking».

**Что сделать (как Fork):**
- Пункт в контекстном меню remote-ветки в сайдбаре: «Отслеживать…» / Track.
- Диалог: remote-ветка (read-only), локальное имя (дефолт = путь без `remote/`, напр. `feature/TiabinIA/AddImportOnPactModal`).
- Команда: `git switch -c <local> --track <remote>/<branch>` или `checkout -b` + `-u`.
- Если локальная ветка с таким именем уже есть — checkout на неё или предупреждение.

**Заметки:** `createBranch` + `setUpstream` отдельно не покрывают UX; remote checkout через `requestCheckout(fullRemoteName)` не заменяет tracking.

**Сделано (2026-06-06):** backend `trackRemoteBranch(remote, remoteBranch, localName)` в `writeCommands` — `git checkout -b <local> --track <remote>/<branch>` через SafetyNet (auto-stash) + preflight, репортит как `checkout` (refresh/тосты/stale-diff уже завязаны). Если локальная ветка уже есть («already exists») — просто checkout на неё, без ошибки. IPC `trackRemoteBranch` + метод в `CommandHandler`. UI: пункт «Track…» в ПКМ remote-ветки (`sidebarMenuItems`), диалог с дефолтом локального имени = путь без `<remote>/`. i18n en/ru.

## Задача 5 — Восстановление активного таба репозитория после перезапуска

**Проблема:** после закрытия и повторного открытия GitBor не возвращает на последний активный таб репозитория — открывается не тот репо или первый в списке.

**Что сделать:**
- При выходе/смене таба надёжно сохранять активный путь (`sg-last-active-repo`) и список открытых табов (`sg-open-repos`).
- При старте: восстановить все табы, затем переключиться на последний активный по пути (не по индексу).
- Проверить гонки при старте (`openRepo` async, `restoreActiveTabAttempted` срабатывает раньше готовности списка).

**Заметки:** задумка уже есть в `recentRepos.ts` + `App.tsx` — фактически не работает у пользователя; искать корень (не пишется при quit, сброс флага, порядок эффектов).

**Сделано (2026-06-06):** корень — гонка восстановления. Старый эффект `restoreActiveTabAttempted` срабатывал на ПЕРВОЕ ненулевое `openRepos` и сразу «тратил» ref; репо открываются асинхронно по одному, и если сохранённый активный путь догружался позже (или поздний `openRepo` крал фокус) — восстановление не происходило. Сохранение работает (эффект на `state.repoPath` пишет при каждой смене таба). Заменил на debounce-таймер (400мс): каждое изменение `openRepos` сбрасывает таймер; срабатываем один раз, когда список стабилизировался → переключаемся на `last` по path (`findRepoIndexByPath`).

## Задача 6 — Доработать «Историю файла» до журнала VS

**Ориентир:** Visual Studio «Журнал» — список коммитов по файлу (идентификатор, автор, дата, сообщение) + действия по коммиту.

**Уже есть и подходит как вход:** пункт **«История файла»** в ПКМ файла, бэкенд `getFileHistory` (`git log --follow`), компонент `FileHistory`. **Новый пункт меню не нужен** — дорабатываем существующий flow.

**Чего не хватает:**
- Сейчас история в **правой панели**, не модалка; клик ЛКМ сразу уводит в diff — нет выбора действия.
- Нет ПКМ по строке коммита.
- Нет «сравнить с предыдущим в списке» / «сравнить с…».

**Что сделать:**
- Расширить `FileHistory` (или обернуть в модалку — на усмотрение UX, можно оставить панель): таблица как в VS, те же данные.
- ПКМ по строке коммита в журнале:
  - **Просмотр** — содержимое файла на этом коммите (или diff этого коммита для файла);
  - **Сравнить с предыдущим** — diff между этим коммитом и предыдущим *в списке журнала* (`git diff <parent>..<commit> -- file`);
  - **Сравнить с…** (опционально) — выбрать любой коммит ниже в списке (старее) и показать diff `старее..новее` для файла; только если не ломает git-логику (путь мог переименовываться — учесть `--follow` / rename в истории).
- Переиспользовать существующий diff/CompareModal где возможно, не дублировать просмотр.

**Заметки:** список в журнале хронологический (новые сверху); «предыдущий в списке» ≠ обязательно `commit^` в графе, но для линейной истории файла совпадает. При rename цепочка `--follow` может дать скачки — сравнение только внутри одного пути или с предупреждением.

**Сделано (2026-06-06):** бэкенд уже всё умел (`getFileDiff` поддерживает одиночный hash, спец-ref `PREV:<hash>` = prev..hash по ревизиям ФАЙЛА, и диапазон `a..b`). Добавил ПКМ-меню на строках журнала (`FileHistory` получил `onContextMenu`, проброшен из `RightPanelContent` ← оба View через `showContextMenu`): «Просмотр изменений» (diff коммита), «Сравнить с предыдущим» (`PREV:<hash>`), «Сравнить с…» (submenu из коммитов ниже в списке → `<old>..<hash>`). Панель оставил (не модалка). i18n en/ru. Rename-цепочки `--follow` не учитываю — сравнение по текущему пути (для линейной истории корректно).
