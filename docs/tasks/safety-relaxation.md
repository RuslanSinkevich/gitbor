# Задача: ослабить safety-сетку, ускорить операции

> Стартовый промпт для нового агентского таба. Скопируй в новый чат.

---

## Проблема

После стрима `feat(safety): классификация ошибок, pre-flight и диалог выбора` (cbdba62) защита от сбоев перебрала. Симптомы на больших репозиториях при беспорядочных переходах по веткам:

- любая операция идёт 3–10 с; в Fork на ~600 файлов — 1–3 с;
- периодически вылетает диалог `index.lock` там, где Fork молча ждёт или ретраит;
- после merge с конфликтами при пост-операциях ловится «lock_held», хотя процессов нет — это stale lock не успевшего отработать механизма;
- нет режима «ничего не делать, я разберусь сам» — диалог навязывает выбор там, где Fork даёт `keep / stash / discard` и идёт дальше.

## Диагноз

Корень не в «слишком много защиты». Корень в том, что защита написана как блокирующая стена, а не как fallback:

1. **`PreflightChecks.checkLock`** (`src/core/safety/PreflightChecks.ts`) при свежем lock (< 15 с) сразу открывает SafetyDialog. Fork ждёт ~500–1500 мс и ретраит, удаляет молча после таймаута.
2. **`OperationQueue`** (`src/core/safety/OperationQueue.ts`) сериализует все write-операции в один поток. Checkout не стартует пока идёт fetch — даже если они в разных воркинг-копиях по сути не конфликтуют. Fork параллелит.
3. **Preflight гоняется перед каждой destructive**: `git status --porcelain` + `git diff --name-only --diff-filter=U` + проверки state-файлов. На репо с тысячами файлов это десятки–сотни мс на ровном месте, ещё до самой команды.
4. **После операции StateManager рефрешит всё** (status + branches + graph + reflog). Каждый рефреш — пачка git-вызовов. Fork делает дельтовые обновления.
5. **`shouldDeferAutoStashRestore`** в `SafetyNet` правильно отложил restore после merge с UU — но повторный `tryRestoreAutoStash` при следующей операции иногда стартует в момент, когда lock ещё держится индексной операцией → ложный «lock_held».

## Цель

Переписать стратегию safety с «блокировать и спрашивать» на «ждать-ретраить, спросить только если реально не можем». Уложиться в Fork-овые тайминги на больших репо.

## Что сделать

### Lock handling

- В `PreflightChecks.checkLock`: при свежем lock не открывать диалог сразу. Ввести `LockWaiter` — exponential backoff retry 100 → 200 → 400 → 800 → 1600 мс (суммарно ~3 с). Если за это окно lock исчез — продолжаем молча. Если нет — тогда уже SafetyDialog с информацией о процессах.
- `STALE_LOCK_AGE_MS` оставить 15 с, но автоудаление делать только если за окно ретраев lock не двинулся (mtime не изменилась).
- Убрать `checkLockMeta` debug-лог из `OperationQueue` — дублирует preflight.

### OperationQueue

- Разрешить параллельный запуск write-операций, если они в **разных рабочих копиях** (разные `repoPath`). Сейчас глобальный `writeRunning` блокирует всё. Заменить на `Map<repoPath, boolean>`.
- В рамках одной репы оставить сериализацию write-операций (это правильно — git не любит конкурентных индексных операций).
- Read-операции (graph, status в фоне) разрешить параллельно write-операции в той же репе — git это терпит, ничего не сломается, только данные могут чуть отставать.

### Preflight

- Сделать preflight ленивым: основной набор destructive операций (`checkout`, `merge`, `rebase`, `pull`, `push`, `cherry-pick`, `revert`, `reset`) — да, оставить. Остальные (`stash`, `tag`, `branch create/delete`, `commit`) — без preflight, ловить ошибку постфактум.
- Кэшировать результат preflight на 500 мс per-repo: если пользователь нажал `checkout` дважды быстро, второй раз не гонять `git status` заново.
- `checkUnmergedPaths` и `checkDirtyTree` запускать в `Promise.all` — сейчас последовательно.

### Post-op refresh

- StateManager после операции рефрешит дельту, а не всё. Минимум: после `commit` — обновить status + последние N коммитов графа (без полного rev-list), не трогать branches если HEAD не сменился.
- Отдельная задача по уровню сложности, но без неё «3–10 с» не уйдут.

### UX

- В SafetyDialog добавить дефолтную опцию «продолжить как есть» (где безопасно) — чтобы Enter сразу делал то, что хочет юзер в 80% случаев.
- Логировать в `mainLogger.info` суммарное время операции (queue wait + preflight + exec + post-refresh) — без этого регрессии перфа не отловим.

## Не делать

- Не убирать `SafetyNet.wrapDestructive` полностью. Журнал и rollback нужны, проблема не в них.
- Не отключать `OperationJournal` — он не на горячем пути.
- Не трогать classification ошибок — она правильная.

## Риски

- Lock-waiter может скрыть реально зависший git: добавить hard timeout 5 с после которого всё равно показываем диалог.
- Параллельные write в разных репах могут пересечься, если юзер открыл одно и то же репо в двух вкладках через симлинк. Не наша забота — пусть падает.
- Ленивый preflight означает что для `stash` ошибки придут от git напрямую — нужно проверить что классификатор их корректно мапит.

## Метрики приёмки

Запустить на репо ≥ 10k коммитов, ≥ 1k файлов в индексе:

- checkout между двумя ветками без локальных изменений: ≤ 1.5 с (сейчас 3–8 с);
- 10 последовательных checkout туда-сюда: ни одного диалога `lock_held`;
- параллельный fetch в одной вкладке + checkout в другой: обе операции не ждут друг друга.
