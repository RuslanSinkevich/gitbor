# Стрим: последовательное выполнение всех задач из `docs/tasks/`

> Стартовый промпт для нового агентского таба. Скопируй в новый чат.

## Правила выполнения (строго)

1. **Никаких субагентов.** Всё делаешь сам в одном контексте. Не делегируй через Task tool.
2. **Никаких вопросов пользователю.** Все решения принимаешь самостоятельно. Если в задаче что-то неоднозначно — выбираешь разумный вариант и идёшь дальше, фиксируя выбор в коммите.
3. **Поочерёдно.** Не параллелишь задачи. Закончил одну — коммит — следующая.
4. **Один коммит на задачу.** Когда задача готова и протестирована — коммит с понятным сообщением, удаление файла задачи из `docs/tasks/` тем же коммитом (он отработал).
5. **Не останавливаться** между задачами. После коммита сразу переходишь к следующей.
6. **Запрещены «божественные» классы и компоненты.** Любая логика разбивается по ответственности.

   **Мягкие лимиты** (повод задуматься, не приговор):
   - `.tsx` компонент — **400 строк**;
   - `.ts` модуль логики — **500 строк**;
   - функция/метод — **80 строк**;
   - публичных методов в классе — **10**.

   **Жёсткие лимиты** (требуют разбиения **или** письменного обоснования в шапке файла, почему атомарно):
   - `.tsx` компонент — **700 строк**;
   - `.ts` модуль логики — **800 строк**;
   - функция/метод — **150 строк**;
   - публичных методов в классе — **15**.

   **Исключения (лимиты не применяются):**
   - словари (`i18n/en.ts`, `i18n/ru.ts`, локали);
   - типы и интерфейсы (`*.d.ts`, файлы только с `export type/interface`);
   - сгенерированный код, тестовые fixtures;
   - barrel-файлы (`index.ts` с одними re-export'ами).

   **Главные принципы важнее цифр:**
   - один файл = одна ответственность. Не складывай в `Sidebar.tsx` логику drag&drop, контекст-меню, persist'а и build-tree одновременно — это разные модули, даже если по строкам помещается.
   - хуки React: если в `useXxx` больше 4 `useState` + 3 `useEffect` или больше 250 строк — разбивай на под-хуки.
   - если задача провоцирует «дописать ещё в существующий файл, который уже у жёсткого лимита» — сначала рефакторинг файла отдельным коммитом, потом фича.
   - класс с методами разных назначений (управление + парсинг + сериализация) — разноси по доменам, не по «размеру файла».

## Порядок выполнения

Жёсткий, не менять:

1. `docs/tasks/safety-relaxation.md` — фундамент, без этого остальное мерить бессмысленно (всё тормозит).
2. `docs/tasks/stat-dirty-files.md` — `git update-index --refresh` в `refreshAll` + UI-fallback для пустышек. Идёт сразу за safety: тот же `RepoStateRefresher`, закрывает ложные `dirty_tree` в preflight, чтобы checkout-local-changes уже работал на чистом status.
3. `docs/tasks/checkout-local-changes.md` — логически продолжает safety: Fork-стиль диалога при dirty tree.
4. `docs/tasks/error-severity-system.md` — переразметка ошибок по уровню важности и source. Должна идти после safety-relaxation (там lock_held спускается в warning) и до dialogs-unification (потому что меняет когда вообще открывать модал).
5. `docs/tasks/ai-provider-robustness.md` — диагностика и обходы для корпоративных Qwen-gateway'ев (system-prompt игнорится). В основном бэкенд + минимальные UI-добавки в `AiSettingsDialog` — успеет до dialogs-unification, та подхватит расширенный диалог в свою миграцию.
6. `docs/tasks/dialogs-unification.md` — UI-инфра по диалогам.
7. `docs/tasks/context-menu-overhaul.md` — submenu, плотность, ограничение ширины меню. Идёт сразу после dialogs-unification (вторая UI-инфра волна) и до stash-ux (тот опирается на компактное меню).
8. `docs/tasks/stash-ux.md` — Apply Stash диалог, double-click, выделение auto-stash. Опирается на готовый SgDialog (задача 6), компактное меню (задача 7) и severity-классификацию конфликтов (задача 4).
9. `docs/tasks/theme-revision.md` — поверх готовых SgDialog и компактного меню. Только светлая тема, шаги 1–6 в порядке.
10. `docs/tasks/branch-drag-and-drop-rename.md` — отдельная фича, не блокирует ничего, идёт последней по UI.
11. `docs/tasks/docs-screenshots-english-only.md` — в репозитории `gitbor-web` (рядом с `gitbor`). Делается последней, т.к. влияет на другой репо и переключение контекста.
12. **Финальный сквозной рефакторинг** — см. раздел «Финальный рефакторинг» ниже. Не отдельный task-файл, а обязательный шаг стрима.

- `?? docs/tasks/checkout-local-changes.md` — это уже **задача стрима №2**, нужно добавить в индекс: `git add docs/tasks/checkout-local-changes.md`.

## Цикл по каждой задаче

```
1. Прочитать docs/tasks/<task>.md целиком.
2. Реализовать всё что там написано.
3. Прогнать тесты (npm test). Если упали — чинить пока не зелёные.
4. Прогнать lint (npm run lint). Чинить ошибки.
5. Прогнать typecheck (npm run typecheck или tsc --noEmit). Чинить ошибки.
6. Прогнать e2e если задача затрагивает Git-flow, UI-modals или сетевые ошибки
   (safety-relaxation, checkout-local-changes, error-severity-system, dialogs-unification):
   npx playwright test (или эквивалент в проекте). Чинить регрессии.
7. Если задача про UI — собрать (npm run build) и убедиться что не упало.
8. git add -A && git commit -m "<префикс>: <короткое описание>"
   - префиксы: feat, fix, perf, refactor, docs, chore — по сути изменения.
   - в тело коммита можно вписать ссылку на закрытую задачу: "closes docs/tasks/<task>.md".
9. git rm docs/tasks/<task>.md (если ещё не удалён) и закоммитить отдельно с docs(tasks): drop <task>, выполнено.
   - либо удалить в том же коммите — на твоё усмотрение, главное чтобы файл исчез.
10. Сразу переходить к следующей задаче из списка.
```

**Бюджет времени.** Wall-clock лимита нет. Идёшь до победного. Единственное ограничение — пункт «Тесты не лечатся за разумное время» из секции «Если что-то идёт не так» (откат конкретной задачи, дальше).

## Финальный рефакторинг

После выполнения всех task-файлов, до закрытия стрима — **обязательный сквозной рефакторинг**. Цель: погасить технический долг, накопленный за 7 фичевых задач, и проверить что архитектурные правила из секции «Правила выполнения» (пункт 6) действительно соблюдены.

### Что сделать

1. **Аудит размеров файлов.** Скриптом / `wc -l`:
   - найти все `.tsx`/`.ts` в `src/` длиннее мягких лимитов (400/500 строк, см. правило 6);
   - для каждого решить: разбить, или оставить — но если файл превысил жёсткий лимит (700/800), обоснование в шапке файла обязательно.
   - исключения по правилу 6 (i18n, типы, fixtures, barrel'ы) не считать.
2. **Аудит дублирования.** Прогнать `jscpd` или аналог. Дубли > 30 строк подряд — выносить в общий модуль.
3. **Аудит `any`/`unknown` без guard.** В TS-коде не должно быть `any` в новой логике из стрима. Заменить на конкретные типы.
4. **Аудит барелов.** В каждой feature-папке должен быть `index.ts` с публичным API. Импорты в стороннем коде только через `index.ts`, не глубже.
5. **Аудит мёртвого кода.** `ts-prune` или `knip`. Удалить неэкспортируемые и неиспользуемые export'ы, появившиеся за стрим.
6. **Аудит тестов.** Покрытие критичных модулей (`SafetyNet`, `OperationQueue`, `GitErrorClassifier`, `useOperationToasts`) — не ниже текущего. Если упало — добить тестами.
7. **Аудит i18n.** Все новые ключи добавлены и в `en.ts`, и в `ru.ts`. Нет «забытых» ключей в одном языке.
8. **Аудит linter/typecheck.** Должно быть полностью зелёным. Если есть `eslint-disable` или `@ts-ignore` — оправдать в комментарии рядом или убрать.
9. **Аудит производительности.** Прогнать сценарий из метрик `safety-relaxation.md` (≤ 1.5 с на checkout). Если регрессия — чинить до закрытия стрима.
10. **Сборка прод-бандла.** `npm run build` для production. Проверить:
    - сборка не падает;
    - размер бандла не вырос больше чем на 10% относительно текущего baseline (если в проекте есть bundle-gate — он должен быть зелёный);
    - сгенерированный installer (если предусмотрен в скриптах) собирается без ошибок.
11. **Синхронизация документации.** Покрыть всё что стрим сломал:
    - `README.md` и `docs/ru/README.md` — обновить упоминания error handling, safety-flow, drag&drop веток если есть;
    - `docs/architecture.md` и `docs/ru/architecture.md` — секции про SafetyNet, OperationQueue, Error classification, severity-систему, UI-kit/SgDialog. Архитектура изменилась — описание должно совпадать.
    - `docs/safety-error-handling.md` — это post-mortem старой задачи. Дополнить разделом «Эволюция 2026: severity + source» с ссылками на новые модули.
    - **Репо `gitbor-web` (`../gitbor-web`)** — отдельный сквозной проход:
       - если визуал светлой темы поменялся (theme-revision) — пересмотреть скриншоты в `public/screenshots/` (после задачи `docs-screenshots-english-only` они уже плоские, без локалей);
       - если изменились формулировки диалогов / тосты ошибок — обновить тексты в `src/content/docs/{en,ru}/*.mdx` (особенно `data-protection.mdx`, `troubleshooting.mdx`, `conflicts.mdx`);
       - если добавились новые фичи (drag&drop веток) — короткий раздел в `getting-started.mdx` или `commit-graph.mdx`.
       - коммитить в `gitbor-web` отдельно, со своим префиксом `docs: sync with gitbor stream <дата>`.

### Правила рефакторинга

- **Не менять поведение.** Только структура, имена, разбиение. Любое поведение, изменённое в рамках рефакторинга, — отдельный коммит с пометкой `fix:`, не `refactor:`.
- **Каждое разбиение — отдельный коммит** с понятным сообщением `refactor(<область>): split X into Y, Z`. Не громоздить в один большой коммит «refactor everything».
- **Тесты должны проходить после каждого коммита**, не только в конце.
- **Не вводить новые абстракции «на будущее».** Только то что реально упрощает текущий код.

### Финальная проверка

После рефакторинга прогнать всё ещё раз: `npm test`, `npm run lint`, `npm run typecheck`, `npm run build`. Всё зелёное — переход к закрытию.

## Завершение стрима

После финального рефакторинга:

1. В `docs/tasks/` должны остаться только `STREAM.md` (этот файл) и `README.md` (если есть).
2. Удалить `STREAM.md` тоже — он отработал. Финальный коммит `docs(tasks): close stream`.
3. Кратко отчитаться пользователю: списком сделанных задач и SHA коммитов, отдельно — что разбито/удалено на рефакторинге.

## Если что-то идёт не так

- **Задача оказалась шире чем описано.** Делаешь минимально-работающий вариант, закрываешь её, излишки выносишь новой задачей в `docs/tasks/<имя>.md` и продолжаешь стрим (новые задачи не подхватываешь автоматически — только если они блокируют текущую).
- **Тесты не лечатся за разумное время (>30 мин).** Откатить изменения, в файл задачи дописать раздел `## Блокеры` с описанием, перейти к следующей. **Не оставлять незакомиченный мусор.**
- **Конфликт с уже сделанным.** Не разруливать через `--force`. Если совсем тупик — откат, фиксация в `## Блокеры`, дальше.

Стрим из `docs/tasks/STREAM.md`. Выполняй задачи в указанном порядке, по правилам выше. Без вопросов, без субагентов.
