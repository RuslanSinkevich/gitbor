## Раздел A. Тормоза при переключении веток

### Кто триггерит «лаг» при `checkout` ветки с большим diff

Маршрут checkout (после успешного `git checkout`):

```
handlersGitOps.checkout  →  Write.checkout
  → safeWrite / gitWrite
    → state.refreshAll(target, { deferHeavy: true })
      → refreshFast (parallel: branches, tags, stashes, remotes, status)
      → mirrorSliceToState + notify        ← UI разлочивается тут
      → refreshGraphProgressive (deferred — fire-and-forget)
        → Phase A: git log --max-count=500  (~50-300 ms)
        → Phase B: git log --max-count=50000 (~5-15 s на больших репо)
```

То есть UI «отпускает» спиннер ПОСЛЕ refreshFast (это правильно), но
после этого начинаются **скрытые проседания** UI:

1. **`git update-index --refresh`** в `refreshStatus` — на 100k tracked-
   файлов выполняется секунды на холодном диске. Делается всегда, даже
   когда status уже актуален.

2. **Phase B `git log --max-count=50000 --all`** при смене HEAD —
   `cachedHeadHash` инвалидируется, поэтому skip-по-headHash не
   срабатывает, и весь log пересобирается с нуля. На монорепо (vscode,
   chromium) это 5-15 секунд git'а + 1-3 s `parseCommits` в worker +
   1-2 s `computeGraphLayout` в worker. Всё это **fire-and-forget**, но
   рендерер всё равно получает финальный `graphData` payload в 3-10 MB
   через IPC и пересчитывает CommitGraph (нодов в WeakMap memo всё
   равно становится в 100x больше → первый render слегка тормозит).

3. **IPC payload graphData** при первом получении 50k коммитов на
   неактивном табе — это разовая обработка через main thread JS engine.
   На больших монорепо это легко 50-200 ms RAF stall.

### Что это, GitBor или VS Code / Visual Studio?

Скорее всего ИХ переключение веток тоже не мгновенное. На монорепо
(сотни тысяч файлов) даже сам `git checkout` без UI выполняется
2–10 секунд: ядро git проходит весь working tree, чтобы обновить
inode-данные. Это OS-уровневая работа, GitBor её только ждёт. Однако
GitBor добавляет сверху Phase B + post-status refresh, что усугубляет
ощущение «всё ещё что-то происходит» в течение 5–15 s после клика.

VS Code и Visual Studio после `git checkout` тоже делают свой full
file watcher rescan + ts language server reanalyze — это занимает
секунды и тормозит весь UI редактора. Поэтому **симптом не уникален
для GitBor**, но архитектурно у GitBor есть три точечных улучшения,
которые сделают переключение явно быстрее VS Code:

### Конкретные рекомендации (без кода, как направление)

1. **`update-index --refresh` сделать опциональным**. На больших репо
   эта команда стоит секунды и делается для каждого `refreshStatus`.
   Триггер: вызывать только когда юзер сам нажмёт «Refresh» или
   `FileWatcher` подцепил изменение файла, не из переключения ветки.
   После checkout `update-index` уже консистентен (git сам обновил
   stat-инфу для затронутых файлов), второй прогон избыточен.

2. **Phase B триггерить только при изменении набора ref'ов**. Сейчас
   любой смены HEAD достаточно. На самом деле `git log --all` зависит
   от ВСЕХ ref'ов, а не от текущего HEAD: если набор ветвей не
   менялся (просто переключились между двумя существующими), Phase B
   почти всегда вернёт идентичный stdout (cacheLogHash сравняется).
   Это сейчас сравнивается, но **после загрузки**, а нужно ДО:
   быстрая проверка `for-each-ref --format=%(objectname)` дешёвая,
   её хеш можно сравнить со старым и решить, нужен ли git log на
   50k коммитов вообще.

3. **GraphLayout — не пересчитывать целиком, если изменились только
   `isCurrentBranch` / `refs`**. Сейчас при смене HEAD пересчитывается
   ВСЁ (parents, columns, branch lanes) для 50k коммитов, хотя
   реально меняется только пара флагов на 2-3 нодах. Это
   архитектурно решается мутацией commits[].refs in-place в
   `RepoStateRefresher` без пересборки layout, но требует
   аккуратной инвалидации WeakMap-кеша в `CommitGraph`.

4. **Перенести parseCommits + computeGraphLayout на воркер с
   IPC streaming**. Сейчас они в worker_threads, но результат
   собирается одним блоком 50k objects и передаётся через
   structuredClone — это 100-300 ms сам по себе на больших репо.
   Streaming через `MessagePort.postMessage` в chunks (по 5000
   коммитов) даёт первое рисование графа быстрее.

5. **Дебаунс multiple checkouts**. Если юзер кликает по нескольким
   веткам подряд, текущий код запускает все Phase B параллельно с
   `slice.token` инвалидацией. Token-guard защищает от пишущих
   мерчей, но git CLI вызовы (`git log --max-count=50000`) уже
   стартуют и едят I/O. Имеет смысл дебаунсить запуск Phase B на
   200-300 ms.

Конкретного приоритета сейчас не назначаю — нужен perf-trace на
реальном проекте юзера (`docs/performance/refresh-investigation.md`
уже есть, но без свежих чисел). Самое дешёвое и с наибольшим эффектом
— пункт 2 (skip Phase B по for-each-ref хешу).

### Что ТОЧНО НЕ GitBor

- Если тормозит конкретный файл при открытии после checkout — это VS
  Code re-analyze (TS server, ESLint, языковой расширения). GitBor
  файлы не открывает.
- Если тормозит сам `git checkout` (даже из терминала) на 5+ секунд —
  это OS-level, ничего не сделать (Windows Defender / антивирус /
  индексатор могут хватать FS).

## Раздел B. Кроссплатформа, фокус на Linux

### Проверено по коду

| Точка | Статус | Заметка |
|---|---|---|
| `process.platform` ветвления | ✅ | win32/darwin/linux все обработаны там, где нужно (open in terminal, /dev/null vs NUL, GitProcessDetector) |
| `os.homedir()` для SSH/AI configs | ✅ | Работает на всех платформах одинаково (`~/`) |
| LongPathSuggester | ✅ | На Linux/macOS пропускается явно (`process.platform !== 'win32'`) |
| GitExecutor → `spawn('git', ...)` | ✅ | Полагается на PATH. На Linux git есть в подавляющем большинстве дистров; `checkGitAvailable` ловит отсутствие на старте |
| `package.json` `build.linux` | ✅ | `target: ['AppImage', 'deb']`, иконка, desktop entry, mime для папок — всё на месте |
| `signtool.exe` упоминания | ✅ | Не зашиты — electron-builder сам выбирает signer по платформе |
| Native modules | ✅ | Нет (`node-gyp`/`prebuilds`/`.node` бинарей). Pure JS Electron app, отлично переносится |
| CI matrix | ✅ | `.github/workflows/release-pack.yml` запускает pack-smoke на ubuntu-latest / macos-latest / windows-latest |
| CRLF/LF в diff-парсерах | ✅ | `ConflictParser`/`DiffParser` нормализуют `\r\n` → `\n` |
| `electron-builder --linux` Linux deps | ✅ | Workflow ставит `libgbm1 libgtk-3-0 libnss3 libxss1 libasound2t64 fakeroot dpkg` |
| `path.sep` в pickDirectory / clone | ⚠️ | `joinPath()` в `cloneDirPersist.ts` определяет разделитель эвристически (наличие `\` в parent → `\`, иначе `/`). На Linux всегда даст `/`. На Windows может дать `/` если parent был введён вручную как `C:/repos` — git это понимает, но edge-case стоит запомнить |

### Найдённые риски на Linux (приоритеты)

1. **`safeStorage` без секрет-сервиса** (низкий-средний риск).
   На голой Ubuntu/Wayland sessions без `gnome-keyring` / `kwallet`
   Electron `safeStorage.isEncryptionAvailable()` вернёт `false`, и
   API-ключи AI-провайдеров будут писаться как `plain:<key>` в
   `~/.config/GitBor/ai-config.json`. Это уже учтено fallback'ом, но
   стоит проверить вручную, что:
   - В headless-сервере (где нет DBus) приложение не падает.
   - В desktop session с keyring всё пишется как `enc:`.

2. **AppImage и MIME `inode/directory`** (низкий).
   В `package.json/build.linux.desktop` указано
   `MimeType: 'inode/directory;'` — это «открыть с помощью GitBor»
   из Nautilus / Files. На некоторых DE (Cinnamon, KDE) это надо
   проверять отдельно. AppImage не интегрируется в desktop без
   `appimaged` или ручной интеграции — это нормальное ограничение.

3. **`spawn('git')` PATH-resolution в AppImage** (низкий).
   AppImage запускается из tmpfs-mount, и PATH может быть урезан в
   некоторых дистрах. `checkGitAvailable` использует system PATH
   (Electron наследует от родителя), но если AppImage запущен из
   GUI-launcher без терминала, PATH может не содержать
   `/usr/local/bin`, `~/.cargo/bin`, и т.п. Этот сценарий встречается
   реже, но если поступит баг-репорт «GitBor говорит git not found,
   а в терминале есть» — это первое место смотреть. Лечится
   `app.commandLine.appendArgument` с принудительным дополнением
   PATH в main.ts.

4. **Иконка**. `resources/icon.png` — placeholder (см.
   `docs/cross-platform-checklist.md`). На AppImage это даст
   generic-иконку в системе. Не блокирующий, но визуально неприятно.

5. **`update-index --refresh` на Linux** (см. Раздел A).
   ext4/btrfs/xfs там в основном быстрее NTFS, но на cloud-FS
   (sshfs, gvfs-smb) — может быть значительно медленнее. Это
   общий «git slow on network FS» риск, для перфа желательно
   делать `update-index --refresh` опциональным как описано выше.

### Что критично проверить руками на Linux

См. `docs/cross-platform-checklist.md` пункты 1-9. Минимальный список,
чтобы сказать «Linux точно взлетел»:

1. `npm run build && npm start` на Ubuntu 22.04 X11.
2. `npm run build && npm start` на Ubuntu 24.04 Wayland.
3. `electron-builder --linux --dir` без подписи (CSC_IDENTITY_AUTO_DISCOVERY=false).
4. Открыть AppImage / `.deb`, открыть существующее репо, сделать commit,
   pull, push, stash, checkout.
5. `git checkout` ветки с >100 файлов diff — проверить subjective
   feeling: лаг похож на Windows-версию (т.е. не _значительно_ хуже)?
6. `~/.ssh/` — генерация Ed25519 ключа из UI, должна создаваться с
   `mode 0o700` (внутри `SshKeyManager`).
7. AI Settings → Ollama (если установлена локально) — проверить, что
   `http://localhost:11434/v1` доступен из приложения. На Linux нет
   firewall-сюрпризов как с Windows Defender SmartScreen.

## Заключение

- По производительности **есть конкретные дёшевые улучшения**
  (пункты A.1–A.5), особенно skip Phase B по for-each-ref хешу —
  он сократит хвост работы после checkout на больших репо
  с 5-15 s до субсекунд.
- По кроссплатформе **критических блокеров нет**. Архитектура
  правильно разнесена (`process.platform` ветки, нет native deps,
  есть CI matrix). Остаётся только реальный запуск на Linux-боксе
  для проверки runtime-аспектов и заодно для перф-замеров против
  Windows-цифр.
