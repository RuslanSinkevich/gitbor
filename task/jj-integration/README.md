# Интеграция с Jujutsu (jj) — исследование и вердикт

**Вердикт: НЕ интегрировать jj в ядро GitBor. Если делать — отдельный проект,
переиспользующий UI-слой GitBor, с собственной моделью состояния.**

Ниже — обоснование, почему прямая интеграция в текущую архитектуру
нецелесообразна, и как выглядит разумная альтернатива.

## 1. Что такое jj (фактология, актуально на 2026)

- Jujutsu — Git-совместимая VCS. Последний релиз **v0.42.0 (июнь 2026)**,
  всё ещё **0.x** — API/поведение без гарантий стабильности.
- Хранилище абстрактно, но **production-ready только Git-backend** (использует
  Rust-библиотеку gitoxide). Коммиты и файлы лежат в обычном `.git`;
  **закладки (bookmarks/ветки) и метаданные — в отдельном хранилище jj вне git**.
- **Colocated-репозиторий** (`jj git init` по умолчанию): рядом `.jj` и `.git`,
  общая рабочая копия. jj автоматически import/export в git на каждой команде.
  Можно смешивать `jj` и `git`, НО jj обычно переводит git в **detached HEAD**
  (в jj нет понятия «текущая отслеживаемая ветка»), и мутации git на живом jj
  не рекомендуются.

## 2. Модель jj принципиально другая, чем у git

Это не «git с другими глаголами». Отличия ломают базовые допущения GitBor:

| Концепт | git (модель GitBor) | jj |
|---|---|---|
| Staging / индекс | Есть (staged/unstaged, hunk-staging) | **Нет индекса вообще** |
| Рабочая копия | Отдельно от коммитов | **Рабочая копия = коммит** (`@`), снапшотится автоматически |
| Ветки | Именованные refs, current branch | **Анонимные по change-id**, bookmarks опциональны |
| Идентификатор | commit SHA | **change-id** (стабилен через rebase) + commit SHA |
| Отмена | reflog / reset | **operation log** (`jj undo`/`jj op`) — отменяет любую операцию |
| Конфликты | Блокируют, надо резолвить сразу | **First-class**: коммитятся, резолвятся когда удобно |
| Stash | Есть | Не нужен (нет индекса, wc — коммит) |

GitBor завязан на git-индекс на **всех** уровнях:
- `messages.ts` — команды `stageFile/stageHunk/unstage/stash/...`, события
  `mergeState` с `conflictFiles`;
- `StateManager`/`RepoStateRefresher` — читают git status/branches/ahead-behind;
- `ConflictManager` — детект `MERGE_HEAD`/`CHERRY_PICK_HEAD`, `git status --porcelain`;
- UI — `LocalChanges`, staging, `CommitBar`, sidebar веток.

Половина этого в jj либо не существует (индекс, stash), либо семантически иная
(ветки → change-id, «текущая ветка» → detached HEAD, отмена → op log).

## 3. Варианты интеграции и почему каждый плохой для ядра

### Вариант А. Встроить `jj-lib` (Rust) в Electron
- `jj-lib` — Rust-крейт. По их же docs: «предназначен для использования из
  GUI/TUI/сервера», но «мало внимания уделено тому, какие символы экспонированы»,
  **стабильного публичного API нет**, не читает пользовательский конфиг.
- Для Electron/TS нужен нативный модуль (napi-rs/neon) + сборка под win/mac/linux,
  версионный ад с 0.x-крейтом. Огромная поверхность обслуживания.
- **Вывод: нет.**

### Вариант Б. Обёртка над `jj` CLI (как GitExecutor над git)
- Рекомендуемый способ интеграции (issue jj#3219). НО:
  **стабильного machine-readable вывода нет.** `jj api`/`--json` — открытый
  запрос, не реализован. Структурированный вывод только через шаблоны
  (`-T 'json(...)'`), и функция `json()` в шаблонах частична.
- Парсинг человекочитаемого вывода jj хрупок и ломается между 0.x-версиями.
- Даже с идеальной обёрткой это **не переиспользует** git-специфичный код
  GitBor: другой граф (change-id, op log), другие «ветки», нет staging.
  Пришлось бы писать параллельный слой команд/состояния/сообщений почти с нуля.
- Есть сторонняя обёртка `agentic-jujutsu` (Rust/WASM, JS-биндинги), но она
  заточена под AI-агентов/MCP, не под desktop-GUI, и тоже поверх нестабильного jj.
- **Вывод: технически возможно, но это отдельная VCS-подсистема, а не «фича».**

### Вариант В. Прямая интеграция в текущий git-клиент (адаптер)
- Попытка сделать jj «ещё одним бэкендом» за существующими IPC-командами
  провалится: команды/сообщения/стейт спроектированы под git-индекс.
  `stageHunk`, `stash`, «current branch», `mergeState.conflictFiles` не имеют
  прямого аналога. Получится дырявый адаптер с кучей no-op и спец-кейсов.
- Colocated-режим (jj+git на одном репо) даёт **гонки состояния**: фоновый
  auto-fetch и watcher GitBor читают/дёргают git, пока jj держит git в detached
  HEAD и импортирует/экспортирует refs. Источник трудноуловимых багов.
- **Вывод: нет — это не рефакторинг, а переписывание ядра.**

## 4. Рекомендация: отдельный проект, общий UI-слой

jj стоит внимания (перспективная модель), но как **самостоятельный продукт**,
а не мутация git-клиента. Оптимальный путь:

1. **Отдельное приложение** (рабочее имя, напр. `jjbor`) с собственной моделью
   состояния под jj: change-id вместо веток, operation log как first-class,
   отсутствие staging, first-class конфликты.
2. **Переиспользовать из GitBor UI-слой**, не VCS-ядро:
   - дизайн-система `src/renderer/src/ui/*` (SgDialog, SgTable, SgSplitPane, ...);
   - рендерер графа `features/graph/CommitGraph` (адаптировать под change-id);
   - diff-компоненты `features/diff/*` и 3-панельный merge-editor
     `features/merge/*` (jj-конфликты тоже текстовые);
   - каркас Electron (main/preload/IPC-мост), i18n.
   Для этого предварительно вынести UI-kit и graph/diff/merge в переиспользуемый
   пакет (сейчас они уже неплохо изолированы — зависят от `types`/`api`, не от git).
3. **Слой команд — новый**, поверх `jj` CLI с шаблонами (`-T 'json(...)'`) для
   структурированного вывода; дизайнить сразу под будущий `jj api`/`--json`.
4. Не запускать jj и git-поллинг GitBor на одном репо одновременно.

Оценка: это R&D-проект (недели-месяцы), не фича на спринт. Разумно **отложить**
до стабилизации jj (стабильный `--json`/`jj api`, выход из 0.x) — тогда обёртка
станет надёжной и объём резко падает.

## 5. Итог для трекера

- В GitBor (git-клиент) jj **не внедряем** — архитектурная несовместимость +
  нестабильность jj 0.x.
- Действие сейчас: **никакого кода**. Пометить как «исследовано, отложено».
- Подготовительный шаг, полезный независимо от jj: вынести UI-kit + graph/diff/
  merge в переиспользуемый слой (снижает связность и в самом GitBor). Это можно
  оформить отдельной задачей, если решим двигаться к сепаратному jj-проекту.
- Ревизия решения — при выходе jj из 0.x или появлении стабильного `jj api`.
