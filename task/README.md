# Задачи-исследования

Индекс исследований по фидбэку из статьи. Каждая задача — отдельная папка.

## 1. Множественный cherry-pick (`multi-cherry-pick/`)

**Вердикт: реализуемо.** Есть детальное ТЗ и разбивка на таски по табам.

Источник (фидбэк TAZAQ):
> Фильтрация коммитов по regexp + массовый cherry-pick. Массовость — чисто
> UX-удобство, черипикается по одному коммиту. При конфликте — модалка со
> списком файлов, дабл-клик по файлу → три редактора (слева/справа/итог).

Значительная часть инфраструктуры уже есть (merge-editor с 3 зонами,
детект `CHERRY_PICK_HEAD`, баннер конфликта, поиск по графу). Нужно добавить:
мульти-выбор в графе, regexp-фильтр, batch-команду поверх git-секвенсера,
кнопки continue/skip/abort для последовательности.

См. `multi-cherry-pick/README.md` и `multi-cherry-pick/tasks.md`.

## 2. Интеграция с Jujutsu (jj) (`jj-integration/`)

**Вердикт: НЕ интегрировать в ядро GitBor. Делать отдельный проект,
переиспользуя UI-слой.** Развёрнутое обоснование и альтернатива — в
`jj-integration/README.md`.

Кратко: jj — не «git с другими глаголами», а другая VCS (нет staging/индекса,
рабочая копия = коммит, change-id вместо веток, operation log). Модель данных
GitBor завязана на git-индекс на всех уровнях (StateManager, IPC-сообщения,
ConflictManager, UI staging). jj 0.x без стабильного API/CLI-JSON. Адаптер
поверх текущего ядра не выйдет — пришлось бы строить параллельную модель.
